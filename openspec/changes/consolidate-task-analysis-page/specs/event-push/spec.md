# event-push Specification (Delta)

## MODIFIED Requirements

### Requirement: 推送规则管理

系统 SHALL 允许管理员创建、查看、编辑、启用/停用、删除推送配置。每条推送配置 MUST 归属且仅归属一个分析任务（1:1），并 MUST 至少包含：所属分析任务、选定的事件类型（`per_item`、`aggregate` 或两者）、一个或多个收件人邮箱、触发方式（`on_run` / `scheduled` / `manual`）、启用状态；当触发方式为 `scheduled` 时 MUST 还包含调度参数（cron 表达式或间隔秒数）。推送配置 MUST 在「任务分析」页的任务编辑弹窗「推送配置」区管理，且仅对拥有 `analysis_tasks` 页面权限的用户可见。每个任务至多一条推送配置；为已存在推送配置的任务再次保存时 SHALL 更新该配置而非新建。

#### Scenario: 创建推送配置
- **WHEN** 管理员在任务 A 的编辑弹窗「推送配置」区勾选事件类型 `per_item`、收件人填 `a@example.com`、触发方式选 `on_run` 并保存
- **THEN** 系统为任务 A 创建一条归属任务 A 的推送配置，状态为启用，任务列表摘要更新

#### Scenario: 触发方式为 scheduled 时必须填写调度参数
- **WHEN** 管理员在「推送配置」区选择触发方式 `scheduled` 但未填写 cron 表达式或间隔秒数
- **THEN** 系统拒绝保存并返回明确的校验错误

#### Scenario: 普通用户无权配置推送
- **WHEN** 未被授予 `analysis_tasks` 页面权限的用户尝试访问「任务分析」页或调用推送配置接口
- **THEN** 系统拒绝访问（前端跳转、后端返回 403）

#### Scenario: 每任务至多一条推送配置
- **WHEN** 任务 A 已有一条推送配置，管理员再次在弹窗「推送配置」区修改收件人并保存
- **THEN** 系统更新任务 A 已有的那条推送配置，不新增第二条

### Requirement: 事件选定与增量水位线

系统 SHALL 把分析结果 `AnalysisResult` 作为推送的「事件」。每次为某条推送配置执行推送时，系统 MUST 选出满足该配置筛选条件（`task_id` 等于该配置所属任务、`result_type` 属于该配置选定事件类型）且 `id` 大于该配置当前水位线的分析结果，作为本次待推送事件集。每条推送配置 MUST 维护一个水位线（上次推送的最大 `AnalysisResult.id`）；推送成功后水位线 MUST 更新为本次推送事件集中的最大 `id`。水位线为空时（首次推送），系统 MUST 推送当前所有满足筛选条件的事件。

#### Scenario: 增量推送只发送新事件
- **WHEN** 配置水位线为 100，本次满足筛选条件的事件为 id 101、102、103
- **THEN** 系统只推送 id 101、102、103 的事件，并在推送成功后将水位线更新为 103

#### Scenario: 首次推送发送全部匹配事件
- **WHEN** 配置水位线为空，当前满足筛选条件的事件有 5 条
- **THEN** 系统推送这 5 条事件，推送成功后水位线更新为其中最大 id

#### Scenario: 仅按所属任务与选定事件类型筛选
- **WHEN** 任务 A 的推送配置只选定了事件类型 `per_item`
- **THEN** 系统只选取任务 A 的 `per_item` 类型分析结果，任务 A 的 `aggregate` 结果与其他任务的结果均不被选中

### Requirement: 手动触发推送

系统 SHALL 允许管理员在「任务分析」页对某任务的推送配置手动触发一次推送。手动推送 MUST 同样遵循增量水位线语义（只推送水位线之后的新事件），并在推送完成后在页面可见推送结果。

#### Scenario: 手动触发推送当前新事件
- **WHEN** 管理员在任务 A 的卡片上点击「立即推送」，此时该任务推送配置水位线之后存在 3 条新事件
- **THEN** 系统立即执行一次推送把这 3 条事件发送到收件人，并在推送历史中记录本次结果

#### Scenario: 无新事件时手动推送提示无内容
- **WHEN** 管理员手动触发推送但该任务推送配置水位线之后不存在新事件
- **THEN** 系统不发送邮件，并在推送历史中记录本次状态为「无新事件」

### Requirement: SMTP 配置分层与页面优先

系统 SHALL 支持两处 SMTP 配置来源：「任务分析」页的全局 SMTP 配置区（持久化到数据库）与 `config/app.json` 的 `email` 段。页面配置 MUST 优先于 `app.json`；当页面未配置时回退使用 `app.json` 的 `email` 段。当两处均未提供发送邮件所需的最小配置（SMTP 主机、发件人；密码按服务器要求）时，系统 MUST 返回明确错误而不静默失败。SMTP 配置中的敏感字段（密码等）在通过接口返回时 MUST 脱敏显示。

#### Scenario: 页面配置优先于 app.json
- **WHEN** 「任务分析」页已保存 SMTP 配置，且 `app.json` 的 `email` 段也配置了 SMTP
- **THEN** 系统发送邮件时使用页面保存的 SMTP 配置

#### Scenario: 页面未配置时回退 app.json
- **WHEN** 「任务分析」页未保存 SMTP 配置，但 `app.json` 的 `email` 段配置了 SMTP
- **THEN** 系统发送邮件时回退使用 `app.json` 的 `email` 段配置

#### Scenario: 两处都缺失时明确报错
- **WHEN** 页面与 `app.json` 均未配置 SMTP 主机等最小必需项
- **THEN** 系统在尝试推送时返回明确错误信息，不发送邮件，且不更新水位线

#### Scenario: 接口返回时密码脱敏
- **WHEN** 管理员通过接口读取 SMTP 配置
- **THEN** 密码等敏感字段以脱敏形式返回，不泄露明文

### Requirement: SMTP 配置管理与连通性测试

系统 SHALL 允许管理员在「任务分析」页的全局 SMTP 配置区读取与保存 SMTP 配置，并提供「发送测试邮件」功能以验证配置是否可用。测试邮件 MUST 发送到管理员指定的测试收件人，测试结果（成功/失败及错误信息）MUST 即时返回给页面。

#### Scenario: 保存 SMTP 配置
- **WHEN** 管理员在「任务分析」页 SMTP 配置区填写 SMTP 主机、端口、发件人、用户名、密码并保存
- **THEN** 系统持久化该配置，后续发送邮件使用该配置

#### Scenario: 发送测试邮件验证配置
- **WHEN** 管理员填写测试收件人并点击「发送测试邮件」
- **THEN** 系统用当前生效的 SMTP 配置向测试收件人发送一封测试邮件，并把成功或失败结果返回页面

### Requirement: 推送历史记录

系统 MUST 为每次推送执行（无论成功、失败或无新事件）记录一条推送历史，包含：所属推送配置（及其归属任务）、触发方式、收件人、推送事件数量、状态（成功/失败/无新事件）、错误信息、执行时间（北京时间显示）。系统 SHALL 在「任务分析」页按任务提供推送历史的查看。

#### Scenario: 成功推送后记录历史
- **WHEN** 一次推送成功发送了 3 条事件
- **THEN** 系统记录一条状态为成功、事件数量为 3 的推送历史，执行时间以北京时间显示

#### Scenario: 失败推送记录错误信息
- **WHEN** 一次推送因 SMTP 错误失败
- **THEN** 系统记录一条状态为失败的推送历史，并保存错误信息以便排查
